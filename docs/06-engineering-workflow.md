# 阶段研发与 Code Review 流程

每个开发阶段都必须完成以下闭环，未满足任何一项时不得宣布阶段完成。

## 1. 阶段入口

1. 在 PRD 中明确本阶段范围、非目标和验收条件。
2. 从上一阶段已推送的 `main` 开始开发。
3. 数据库、API 和页面变更保持可追踪关系。

## 2. 实现与验证

1. 完成功能实现及必要的自动化测试。
2. 运行后端测试：`cd backend && mvn test`。
3. 运行前端生产构建：`npm run build`。
4. 检查工作区：`git diff --check` 和 `git status --short`。

## 3. Code Review 门禁

Review 至少覆盖：

- 业务正确性与异常路径
- 数据一致性、事务、幂等和并发
- 认证授权、输入校验和敏感信息
- 模块边界与未来扩展性
- API 契约和前后端字段一致性
- 页面加载、空状态、错误状态和交互反馈
- 测试有效性、依赖风险和配置可移植性

问题级别：

- P0：阻断发布，必须立即修复。
- P1：高风险问题，本阶段必须修复。
- P2：一般问题，原则上本阶段修复；延期必须记录原因。
- P3：建议改进，可进入后续计划。

每次 Review 在 `docs/reviews/` 下生成报告，记录审查范围、发现、修复提交、验证命令和剩余风险。P0/P1 未清零时不得推送阶段完成版本。

## 4. 提交与推送

1. 将功能、测试、文档和 Review 报告一并提交。
2. 提交信息包含阶段或业务域，例如 `feat(stage-02): implement identity and catalog`。
3. 推送 `main` 到 GitHub。
4. 使用 `git ls-remote` 回读远端提交，确认与本地 `HEAD` 一致。
5. 确认 GitHub Actions 的 Quality Gate 通过。

## 5. 阶段完成汇报

阶段汇报必须包含：功能成果、Review 发现与修复、测试结果、本地和远端提交哈希、已知限制及下一阶段目标。
