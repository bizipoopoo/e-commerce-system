# Stage 06 售后、互动与运营工作台 Code Review

## 审查范围

- 售后申请、审核、驳回、寄回和退款状态机
- 订单 `REFUNDING/REFUNDED` 状态、驳回恢复和退款时间线
- 退款记录、库存回补、重复退款与事务原子性
- 跨用户订单/售后隔离和运营接口权限
- 收藏、真实购买评价、运营回复/隐藏和并发修改
- 经营看板、订单发货、售后、库存、营销、内容、评价和消息工作台
- 商城收藏、售后申请、寄回、进度和评价交互
- Stage 06 自动化测试与运行态浏览器验收

## Review 结论

- P0/P1：未发现遗留问题。
- 退款完成以售后单悲观锁串行化，订单、退款记录、库存回补和通知处于同一事务；重复退款直接返回原结果，不会再次回补库存。
- 售后驳回会从持久化的申请前订单状态恢复，避免统一恢复到错误状态。

## Review 发现

| 级别 | 发现 | 处理结果 |
|---|---|---|
| P2 | 收藏接口只校验商品 ID 存在，用户可通过猜测 ID 收藏草稿或已归档商品 | 收藏前改为校验商品必须处于 `PUBLISHED`，并增加草稿商品不可收藏的 API 回归测试 |
| P2 | 评价回复和隐藏没有版本控制，并发运营操作可能产生最后写入覆盖 | `product_reviews` 增加 `version` 字段并启用 JPA 乐观锁；冲突统一返回 `CONCURRENT_MODIFICATION` |
| P2 | 运营端登录后若新售后产生，进入售后列表虽能看到数据，但侧栏待审角标仍保留旧值 | 每次加载售后工作台都根据真实列表同步待审核数量，审核动作后的角标也即时更新 |
| P2 | 退款幂等仅靠实现推导，缺少重复请求与库存精确回补的自动化证明 | 增加退款前后库存断言并重复调用退款接口，验证库存只回补一次、退款单号稳定存在 |

## 验证结果

- 后端：`mvn test` 通过，共 20 个测试；包含模块边界、退款/退货、驳回恢复、跨用户隔离、重复退款、库存回补、收藏、真实购买评价、运营回复/隐藏、管理权限和看板聚合。
- 前端：`npm ci` 与根目录 `npm run build` 通过；商城端和运营端 TypeScript 检查及生产构建成功。
- 浏览器：真实完成用户注册、收藏、收藏夹加购、下单支付、整单退款申请、运营审核、模拟退款、订单状态与消息回读；退款金额 ¥429，订单最终为“已退款”。
- 运营端：登录、真实指标、售后工作台、营销活动和内容运营页面完成视觉与交互验收。
- Diff：`git diff --check` 在提交前执行并确认。
- GitHub Actions：推送后确认 Quality Gate。

## 已知限制

- 当前仅支持整单全额退款；部分商品、部分金额、多次售后和补差价留待正式版本。
- 退款渠道、退货物流和库存质检均为可替换的 Mock 实现，没有真实外部资金和物流交互。
- 同一订单当前只保留一张售后单，驳回后由运营线下补充处理，不支持用户再次发起新售后单。
- 经营看板采用当前库实时聚合，适合 Demo 数据量；规模增长后应改为统计事实表和异步指标管道。
- 运营端采用单一管理员角色，细粒度 RBAC、数据权限和审计导出将在正式化阶段扩展。
